Implementation checkpoint, 2026-10-02. Hosted harness/verifier, productive Sofie Work, Mac-off, browser reconnect and P0 remain **NOT_RUN**. Paid model calls: zero. Production admission/publication: DISABLED.

The existing canonical cloud Run now pins the protected policy hash in FactoryVersion. After candidate custody is validated and the producer sandbox is destroyed, Factory claims one verifier resource in its own database. It allocates a separate digest-pinned, deny-network sandbox with no injected credentials and runs candidate code under `factoryverifier`, separate from the trusted host comparison. Protected expected values stay in the controller. The producer receives neither verifier material nor identity.

Migration 006 stores only Factory verification state: candidate/tree/custody/policy/image binding, bounded lease/deadline, provider identity, check outcomes and cleanup. Claims serialize with existing canonical dispatch. An unresolved verifier prevents another productive allocation; duplicate deliveries cannot allocate a second verifier. Cancellation and expiry fence outcomes. Lost allocation receipts wait until the bounded allocation window has elapsed before exact-name cleanup reconciliation. No repair/replacement allocation occurs during recovery.

The canonical signed Result has an optional strict `verification` field for cloud snapshots only. It distinguishes visible producer checks from independent protected outcomes without another Work/Result system or another signing credential. It binds the exact candidate, Work generation, policy, distinct producer/verifier resources and teardown. It contains no protected inputs, expected outputs, credentials or raw provider errors. Legacy snapshot V1 remains strict. A producer can complete while protected checks fail; MyEve must project that failed verification and cannot infer Ready from producer completion.

The MyEve consumer rechecks the current scoped Gate C admission and current signing keys, then projects signed protected outcomes into the existing Evidence/DirectVerificationDriver contract. Recovery reprojects the already-destroyed verifier receipt; it cannot call local Docker or allocate another cloud verifier. Runtime composition remains guarded until its separate qualification is complete.
