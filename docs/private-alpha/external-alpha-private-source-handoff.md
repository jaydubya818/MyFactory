# External-alpha private source handoff

This protocol preserves the recorded Alpha Tasks scope and authorizes no activation, publication, paid operation, additional tester or production change. External alpha accepts only configured slots 1 and 2. The existing public/canary source mode remains separate.

The operator supplies a byte-digest-pinned `EXTERNAL_ALPHA_PRIVATE_SOURCE_REGISTRY_V1` registry through exactly one of `FACTORY_EXTERNAL_ALPHA_PRIVATE_SOURCE_REGISTRY_JSON` or `FACTORY_EXTERNAL_ALPHA_PRIVATE_SOURCE_REGISTRY_FILE`, plus `FACTORY_EXTERNAL_ALPHA_PRIVATE_SOURCE_REGISTRY_SHA256`. Each entry contains exactly `slot`, `owner`, `repo`, `commit` and `tree`. The owner is a valid repository-owner name; the authorized identity comes from the reviewed registry digest and exact installation binding. No public owner constant, repository-name resemblance or incoming Work parameter grants access.

Pre-staged snapshots use a separate byte-digest-pinned manifest: exactly one of `FACTORY_EXTERNAL_ALPHA_PRIVATE_SNAPSHOTS_JSON` or `FACTORY_EXTERNAL_ALPHA_PRIVATE_SNAPSHOTS_FILE`, plus `FACTORY_EXTERNAL_ALPHA_PRIVATE_SNAPSHOTS_SHA256`. Its shape is `{version:1,kind:"EXTERNAL_ALPHA_PRIVATE_SNAPSHOTS_V1",entries:{...}}`; entries exactly match the configured registry slots. Every receipt contains exactly `repository`, `commit`, `tree`, `path`, `sha256` and `bytes`. The path is `factory/private-source/<slot>/<sha256>.json`. Source bytes, repository credentials and signing keys are absent from this manifest. File inputs require an absolute normalized path, a regular non-symlink final component and no group/world write permission.

Composition fails when a registry or manifest is missing, substituted or inconsistent with the installation. This includes trusted injected-provider fixtures. The hosted entry also loads the independently pinned protected verifier profile before opening its database or provider dependencies.

After accepting recovery delivery and validating the current resource lease, the lifecycle reads private custody before allocating a sandbox. It independently checks receipt length/digest, canonical snapshot structure, owner/repository, Git commit object, reconstructed tree and bounded file contents. Resource evidence contains only the source receipt and commit/tree identities. The producer receives credential-free snapshot bytes, reconstructs the exact base offline, removes snapshot staging files and runs without GitHub network access. The protected verifier independently reads the original source custody again and requires the candidate's base and source files to match it. Producer-supplied source files cannot establish their own authority.

Retrieval runs without ambient Git credentials or global helpers. Timeout/byte-limit failures terminate the Git process group and await closure before bounded cleanup. Provider/storage failures escape as controlled codes rather than private URLs, credentials or temporary paths.

For offline qualification, `cloudWorkProvider` accepts SDK-only `sandboxApi`, `blobPut` and `blobGet` dependencies. They preserve actual harness installation, source reconstruction, execution, candidate validation, custody and cleanup confirmation. `externalAlphaRuntimeComponents` accepts a trusted `providerFactory({spend,plan,privateSource,assertWorkAuthorized})` dependency to use the real runtime ledger with those transports. It is mutually exclusive with `provider` and is never HTTP request or deployment configuration input. Missing cleanup confirmation or custody proof continues to fence completion.

Focused qualification exercises byte-pin/shape/slot denial, owner/base/tree/workspace substitution, custody corruption, allocation denial, independent verifier reread, bounded retrieval and real PostgreSQL authority/delivery replay. Provider transport remains offline and paid model calls remain zero. Installation and activation still require the other release gates and the recorded owner/operator qualification.

## Dedicated host installation

External alpha requires its own Factory project, database resource and private Blob store. `FACTORY_EXTERNAL_ALPHA_HOST_INSTALLATION_JSON` contains exactly `version`, `factoryId`, `environment`, `ownerScope`, `projectId`, `teamId`, `custodyStoreId` and `databaseResourceId`; `FACTORY_EXTERNAL_ALPHA_HOST_INSTALLATION_SHA256` pins the exact JSON bytes. The accepted Factory id is `myfactory-external-alpha`, the environment is `production`, and the owner scope is `external-alpha:<cohortId>`. Vercel's actual project and organization must match. Existing canary, staging, caller projects and canary/staging stores are denied. Canary, qualification and deterministic configuration cannot establish this host identity. Public source contains no external tester resource values.

Apply the full canonical migration manifest to the new empty database, including `012-external-alpha-host-registration.sql`, before explicit host initialization. The additive migration preserves the exact legacy marker predicate and leaves its historical checksum unchanged. It creates an empty immutable host-registration table and a composite foreign key binding the external marker to that exact registered project/cohort/store/database tuple. The explicit `initializeProductionDatabase` operation validates the dedicated tuple, locks application tables and refuses any qualification history before inserting registration and marker atomically. Requests never register a host. Identical initialization is idempotent; competing tuples cannot both install. A bound external marker cannot be retargeted, deleted or demoted, and an existing production canary cannot be promoted to external alpha. This schema/installation operation creates no Work authority or grant.

The shared installation loader accepts two exact source bases within one cohort and source build digest. Each slot retains its own FactoryVersion, independently recomputed from the same source digest plus its exact execution configuration. Even identical source trees with different base commits produce separate versions. Substituting the other slot's base, manifest, custody or FactoryVersion is denied; a shared build does not merge owner authority.

The private-source producer binds SDK operations to its single admitted Session. Command, file and network-policy operations use Session methods directly, avoiding the SDK's automatic resume behavior. A replacement session fences operations; resume, timeout extension, interactive access and snapshot APIs are denied. Public/canary source mode retains its existing provider path.

The protected verifier's hidden suite remains host-only custody. Hosted installations may provide `FACTORY_EXTERNAL_ALPHA_VERIFIER_CUSTODY_JSON`, an exact `{probeBase64,suiteBase64}` payload with canonical base64 and at most 65,536 UTF-8 bytes, instead of a host directory. The canonical loader verifies the pinned combined digest and imports only those same verified bytes. Set this sensitive server input only on the dedicated Factory control-plane host; never place it in tester configuration, producer prompts, source snapshots, sandbox files or public source. Verify the host's complete environment quota before installation. Missing or corrupt hidden custody makes verification partial and prevents acceptance.
